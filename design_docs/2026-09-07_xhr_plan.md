## Purpose

`XMLHttpRequest` is undefined in the runtime, so every one of the 348 files in
the WPT `xhr` directory that touches it fails at its first statement. The
directory scored 53 of 1,013 subtests, and all 53 came from the five
`xhr/formdata/*.any.html` files, which exercise `FormData` and never construct
an `XMLHttpRequest`.

XHR is not a second network path. It is a state machine — `readyState`,
`readystatechange`, progress events, abort and timeout — over the request and
response objects the fetch bootstrap already builds. This lane implements it
there, in `components/script-runtime-api/fetch.rs`, so that one host seam
(`FetchHandler`) still carries every byte the runtime sends or receives.

- `responseType`, `response`, `responseText`, `responseXML`,
  `overrideMimeType`.
- `timeout` / the `timeout` event, `abort` / the `abort` event,
  `withCredentials`.
- Progress events on the request and on `upload`.

### X2 — synchronous send

Sync XHR drives the host to completion inside `send()`. A synchronous host
(and the no-handler default, which is an inline network error) already answers
in the same tick; a deferred host needs a blocking seam.
`FetchHandler::fetch_blocking` is that seam, defaulting to the trait's own
`fetch`, and `__fetch_sync` is the native sink behind it.

The spec restrictions hold: `timeout` and `responseType` are an
`InvalidAccessError` on a synchronous request, and a network error throws
(`NetworkError`) rather than firing `error`.

**Done-conditions**

- A sync send against a synchronous host returns the body from `send()`.
  **Met.**
- `cargo test -p genet-wpt --features netfetch` green with the deferred host's
  blocking implementation. **Met.**

## Findings

Dated 2026-09-07, verified in this checkout.

### F1 — XHR needs no network of its own

Everything the state machine sends or receives goes through `fetch()` (async)
or the one new blocking sink (sync), so `FetchHandler` remains the single seam.
An async `send()` builds a `Request` from the same `extractBody`, the same
`Headers` with the same forbidden-request-header predicate, and an
`AbortController` whose signal carries `abort()` and `timeout` to the host. The
response is the same `Response`, read once with `arrayBuffer()`; every
`responseType` is a view over those bytes.

The one thing that had to be added is a *blocking* seam.
`FetchHandler::fetch_blocking` defaults to the trait's own `fetch`, which is
right for a synchronous host and for the no-handler case (an inline network
error, which is what disk mode is). The deferred host in `ports/genet-wpt`
overrides it, driving the same worker job to `Close` on a private channel, with
its routing id lifted out of the JS id space so a pull credit cannot land on a
deferred fetch that is still registered.

### F2 — an in-flight fetch was freezing every timer

`__runTimers` (`components/script-runtime-api/lib.rs`, the event-loop bootstrap)
broke out of its loop whenever `__pending` was non-empty. That is correct in
**cooperative** mode, where timers fire in delay order ignoring real time and an
in-flight fetch must hold the queue so `testharness.js`'s far-future timeout
does not run first. In **real-time** mode the `at > vnow` gate already does that
job, and the unconditional break meant no timer could ever fire while a fetch
was outstanding — which is exactly when an XHR `timeout` (and
`AbortSignal.timeout`) must fire. The guard is now `!realtime`-only.

This cannot move the disk census: with no handler installed every fetch answers
inline, so `__pending` is empty at every turn. Both drive loops in
`ports/genet-wpt/src/harness.rs` pass `Some(now_ms)`, so the change is confined
to what a live fetch does to timers in server mode.

### F3 — WebIDL enumerability is observable

`xhr/progressevent-interface.html` asserts that `for (p in window)` never yields
`ProgressEvent`. The bootstrap's usual `globalThis.X = X` makes the property
enumerable, which turned a vacuous pass (the interface did not exist) into a
failure. The four interfaces this lane adds are installed with
`Object.defineProperty` instead — non-enumerable, configurable, `prototype`
non-writable, `length` counting only required arguments. The pre-existing
globals were deliberately left alone: changing them would move the `fetch`
baseline for a reason unrelated to this lane.

### F4 — `responseXML` is structurally out of reach, not merely unimplemented

`responseXML` and `responseType = "document"` return `null`. The scripted tier
has no `DOMParser` and no way to build a second `Document`, so there is nothing
to hand back; `xhr/responsexml-*` stays failing until a parser seam exists.
This is named rather than faked.

### F5 — what the remaining disk-mode residual is

All 28 remaining `error` files are `Worker` / `SharedWorker` demand
(`Worker is not defined`) or `document.domain` / multi-window navigation — a
different lane's surface, not XHR's. The 252 still-failing files are dominated
by tests that need the WPT server's Python handlers (`resources/*.py`), which
disk mode cannot serve; the server-mode run below is the evidence.

## Open, for whichever lane owns it

- `responseXML` / `responseType = "document"` need a parser seam (F4).
- Worker-hosted XHR is the whole remaining `error` class: `Worker` is undefined
  (F5), which the census already lists at 51 files across the tree.
- Text decoding covers UTF-8 and the one-byte-per-code-point labels only. A
  response in Shift_JIS decodes as UTF-8; `xhr/overridemimetype-*-shiftjis` is
  a known casualty and needs a real encoding registry.
- Upload progress is synthetic: the events fire in the right order with the
  right totals, but the host seam reports no in-flight upload position.
- The `ProgressEvent` attributes are instance data properties, not prototype
  accessors, so `xhr/progressevent-interface.html`'s three descriptor subtests
  still fail. Fixing that is a WebIDL-shape question for the whole bootstrap,
  not an XHR one.
